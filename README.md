# Демонстрационный прототип управления кэшбэк-офферами

Репозиторий: [Hrusha-demiLTZ/cashback-offers-managment](https://github.com/Hrusha-demiLTZ/cashback-offers-managment). Проект подготовлен для локального прототипа процесса управления офферами повышенного кэшбэка. Основные требования продукта зафиксированы в [ТЗ](02_ТЗ_кэшбэк-офферы_MVP_MVPplus.md), технический подход — в [плане решения](03_Решение_кейса_технический_план.md), последовательность работ — в [плане реализации](05_План_конкретных_задач_реализации.md).

> Это изолированная демонстрационная заготовка, а не банковская система. Будущие клиенты, покупки и начисления должны быть синтетическими; реальные банковские интеграции и движение денег исключены.

## Текущая стадия

Этап 1 — подготовка репозитория и рабочей среды — завершён для имеющегося каркаса. Настроены отдельная локальная PostgreSQL в Docker Compose, GitHub Actions и защита `main`; проект опубликован в правильной структуре корня, а чистый clone `main` проверен. API, веб-интерфейс, бизнес-функции и зависимости приложения ещё не реализованы. Docker Compose поднимает **только базу данных**. Workflow проверяет закреплённые версии Python/Node.js, наличие стартовых файлов, правила для `.env` и синтаксис Compose; он не запускает тесты или сборку приложения, которых пока нет.

## Git, ветки и CI

- Основная ветка GitHub — `main`; рабочая ветка для изменений — `development`. Изменения в основную ветку следует вносить через Pull Request после успешных обязательных проверок.
- GitHub Actions workflow находится в `.github/workflows/ci.yml`; он запускается для Pull Request в `main`, push в `main`/`development` и вручную. Пока приложение и зависимости не созданы, CI ограничен проверкой каркаса, закреплённых runtime и конфигурации Compose.
- `main` защищена: изменения принимаются через Pull Request, успешная проверка `Scaffold and pinned runtimes` обязательна, force-push и удаление ветки запрещены; обязательного одобрения второго участника нет. Защита применяется и к администраторам.
- Существующая история GitHub сохранена: исходный коммит `98f15cad` включён в историю merge-коммита. PR №1 слит merge-коммитом `9664adc`; `main` и `development` синхронизированы на этом commit. Force push не использовался.
- Чистый clone `main` проверен: README, Compose и workflow лежат в корне, `.env` отсутствует, рабочее дерево чистое.

Проверить локальный статус и последние коммиты:

```powershell
git status --short --branch
git log --oneline --graph --decorate -8
```

Не добавляйте `.env` в индекс; перед коммитом проверяйте только выбранные файлы через `git status` и `git diff --cached`.

### Python и Node.js

Python закреплён в `.python-version`. Установить указанную версию в пользовательскую среду через `uv` можно командой:

```powershell
uv python install 3.14.8
```

Node.js закреплён в `.nvmrc`. Для Windows скачать официальный Node.js `24.22.0` LTS, проверить опубликованный SHA-256 и распаковать архив в пользовательский каталог:

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File .\scripts\setup-node-lts.ps1
$nodeHome = Join-Path $env:LOCALAPPDATA 'cashback-offers-toolchains\node-v24.22.0-win-x64'
$env:PATH = "$nodeHome;$env:PATH"
node --version
npm --version
```

Изменение `PATH` действует только в текущей PowerShell-сессии. Не запускайте установщик от имени администратора; скрипт не изменяет системную установку Node.js и отказывается перезаписывать уже существующий каталог.

## Локальный запуск базы (Windows PowerShell)

Требуются установленный и запущенный Docker Desktop с Linux containers, Git, Python и Node.js. Команды ниже не устанавливают приложение и не запускают API/UI.

1. Создать локальный `.env` со случайным паролем базы:

   ```powershell
   powershell -NoProfile -ExecutionPolicy Bypass -File .\scripts\setup-local-env.ps1
   ```

   Скрипт завершится ошибкой, если `.env` уже существует: он не перезаписывает локальные настройки или секреты. Чтобы обновить существующий файл, измените его вручную после создания резервной копии.

2. Запустить базу и проверить её состояние:

   ```powershell
   docker --context default compose up -d db
   docker --context default compose ps
   docker --context default compose logs db
   ```

   Подключение с хоста доступно только через `127.0.0.1:5433`. Будущий backend в Compose должен подключаться к `db:5432`, используя `DATABASE_URL` из `.env`, а не к `localhost` или системной PostgreSQL.

3. Остановить только сервисы этого Compose-проекта, сохранив данные:

   ```powershell
   docker --context default compose down
   ```

   **Не запускайте `docker --context default compose down -v`, если не хотите удалить локальный том `cashback-offers-local-pgdata` и все данные этой демонстрационной базы.** Не выполняйте команды удаления томов для чужих Compose-проектов.

`.env` игнорируется Git. Не добавляйте его, реальные данные или секреты в репозиторий. `.env.example` содержит только placeholders и предназначен для документирования конфигурации.

## Границы и следующие шаги

- Используются только синтетические демонстрационные данные; реальные банковские, платёжные и клиентские системы не подключаются.
- Не добавляйте Redis, Kubernetes или брокер сообщений без отдельной подтверждённой необходимости.
- В этой оболочке команды `python` и `node` указывают на Python `3.14.7` и Node.js `26.7.0`; используйте закреплённые проектом Python `3.14.8` и Node.js `24.22.0`. Обе закреплённые версии реально установлены локально и прошли проверку GitHub Actions. Совместимость с ещё не выбранными зависимостями приложения будет проверена при их фиксации.
- По мере появления backend/frontend в CI нужно добавить locked install, форматирование, lint, typecheck, тесты и сборку, затем включить их в обязательные проверки PR.
- Не выполняйте force push. При интеграции уже существующей удалённой истории сначала проверьте целевой remote/коммит, создайте резервную ветку и просмотрите результат слияния.
