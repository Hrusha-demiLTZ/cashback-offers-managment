# Базовый шаблон банковского хакатон-проекта

> **Назначение:** стартовый комплект решений и копируемых шаблонов для быстрого начала прототипа банковского хакатона. Основан на кейсе управления кэшбэк-офферами и пригоден как отправная точка для других внутренних демонстрационных сервисов.
>
> **Важно:** это не готовый банковский production-boilerplate и не гарантия соответствия конкретным требованиям ИБ. Не использовать реальные клиентские/банковские данные или production-секреты. Перед реальным внедрением нужны ревью архитектуры, угроз, инфраструктуры и нормативных требований.

## 1. Принципы быстрого старта

1. Сначала зафиксировать цель демонстрации, пользователей, основной happy path и минимум три негативных сценария.
2. Выбрать модульный монолит и одну реляционную БД, если нет обоснованной потребности в распределённой системе.
3. Backend и база данных — источник истины. Frontend не является границей безопасности.
4. Контракт API зафиксировать через OpenAPI; frontend-клиент генерировать из контракта.
5. Использовать синтетические данные и повторяемый seed, не случайную генерацию как единственный приёмочный набор.
6. Поднять локальную среду одной командой через Compose; иметь явную команду остановки и сброса только локального тома проекта.
7. С первого дня подключить форматирование, lint, типизацию, тесты, coverage-отчёт и CI.
8. Не включать технологии «на будущее» без конкретного сценария и владельца эксплуатации.

## 2. Среда и рекомендуемый стек

### Проверенное в окружении на момент подготовки шаблона

- Python: `3.14.7`
- Node.js: `v26.7.0`
- Docker: `29.8.2`
- В репозитории исходного кейса уже есть отдельный PostgreSQL, поэтому локальный хакатон-проект должен использовать собственный контейнер, базу, пользователя, порт и volume.

Версии окружения могут отличаться у других участников. Не полагаться только на локальную машину: версии и совместимость должны проверяться в CI.

### Рекомендуемый набор для этого кейса

| Уровень | Язык/технология | Назначение |
|---|---|---|
| Backend | Python, FastAPI, Pydantic | HTTP API, валидация запросов, OpenAPI |
| ORM и миграции | SQLAlchemy 2, Alembic | Работа с PostgreSQL, контролируемая схема БД |
| Frontend | TypeScript, React, Vite | Адаптивный интерфейс |
| UI | MUI или согласованная библиотека компонентов | Русскоязычные внутренние и клиентские экраны |
| СУБД | PostgreSQL | Единственный источник истины для бизнес-состояния |
| Тестирование | pytest, HTTPX, pytest-cov; Playwright для критичных UI-путей | Unit-, API-, интеграционные и сквозные проверки |
| Качество Python | Ruff, mypy (или выбранный единый type checker) | Форматирование, lint, статическая типизация |
| Качество frontend | ESLint, Prettier, TypeScript | Lint, форматирование, проверка типов |
| Генерация данных | Faker с фиксированным seed плюс вручную заданный сценарий | Синтетическое тестовое наполнение |
| Контейнеры | Docker, Docker Compose | Воспроизводимый локальный запуск |

Redis, брокер сообщений, Kubernetes и микросервисы не входят в минимальный набор. Добавлять их, только если выбранный сценарий реально проверяет очередь, кэширование, конкурентную нагрузку или оркестрацию.

### Версии и зависимости

Версии библиотек быстро меняются, а совместимость Python 3.14 зависит от конкретных релизов пакетов. Поэтому:

- в `pyproject.toml` задавать допустимые диапазоны и минимальную версию Python, прошедшую CI;
- фиксировать конкретные разрешённые версии lock-файлом `uv.lock`;
- для Node.js фиксировать версии lock-файлом `package-lock.json` и устанавливать через `npm ci`;
- не использовать `latest` в Docker-образах;
- выбрать поддерживаемый Python, который реально проходит полную установку и CI; проверить 3.14.7, а при несовместимости выбрать ближайшую поддерживаемую версию, например 3.13.x;
- одинаково закреплять выбранную версию Python в CI, Docker и локальной инструкции.

## 4. Шаблон `backend/pyproject.toml`

Это образец состава зависимостей, а не lock-файл. Перед стартом сформировать `uv.lock` и проверить совместимость выбранной версии Python.

```toml
[project]
name = "bank-hackathon-api"
version = "0.1.0"
description = "Synthetic-data demonstration API"
requires-python = ">=3.13,<3.15"
dependencies = [
  "fastapi",
  "uvicorn[standard]",
  "pydantic-settings",
  "sqlalchemy[asyncio]",
  "asyncpg",
  "alembic",
  "psycopg[binary]",
  "pwdlib[argon2]",
  "PyJWT",
]

[dependency-groups]
dev = [
  "pytest",
  "pytest-cov",
  "pytest-asyncio",
  "httpx",
  "ruff",
  "mypy",
  "faker",
]

[tool.ruff]
line-length = 100
target-version = "py313"

[tool.ruff.lint]
select = ["E", "F", "I", "UP", "B"]

[tool.pytest.ini_options]
testpaths = ["tests"]
addopts = "-ra --strict-markers"
asyncio_mode = "auto"

[tool.coverage.run]
branch = true
source = ["app"]

[tool.coverage.report]
show_missing = true
skip_covered = false
fail_under = 80
```

Пример предполагает async-драйвер `asyncpg`; не подключать параллельно разные способы работы с БД без причины. Проверить выбранную схему транзакций и инструмент миграций. `fail_under = 80` — стартовый порог для демонстрационного проекта, а не банковский стандарт: дополнительно перечислить в тест-плане сценарии, которые должны быть покрыты.

## 6. Шаблон конфигурации `.env.example`

Файл содержит только имена и безопасные локальные примеры. Реальный `.env` не коммитить.

```dotenv
APP_ENV=local
APP_NAME=bank-hackathon
APP_LOG_LEVEL=INFO
APP_TIMEZONE=Europe/Moscow

# Локальная изолированная БД Compose; не подставлять URL другой среды.
POSTGRES_DB=hackathon_demo
POSTGRES_USER=hackathon_app
POSTGRES_PASSWORD=local_only_change_me
DATABASE_URL=postgresql+asyncpg://hackathon_app:local_only_change_me@db:5432/hackathon_demo

# Локальный демонстрационный секрет. Сгенерировать новый случайный секрет,
# не использовать это значение в тестовом или production-окружении.
JWT_SECRET=replace_with_random_local_secret_at_least_32_chars
JWT_ISSUER=bank-hackathon-local
JWT_ACCESS_TOKEN_MINUTES=30

FRONTEND_ORIGIN=http://localhost:5173
SEED_DEMO_DATA=false
```

В реальном приложении `JWT_SECRET` не должен иметь fallback-значения в коде. Секреты тестового стенда хранить в secret store платформы CI/CD. Для банковской аутентификации в production предусмотреть корпоративный IdP/OIDC и согласованную политику токенов, MFA и сессий; самодельный JWT login из хакатона не считать готовой корпоративной аутентификацией.

## 8. Шаблон `compose.yaml`

Демонстрационный Compose для локального запуска. Использует выделенные имя контейнера, сеть, том и порт. Перед запуском убедиться, что порт `5433` свободен. Не подключать Compose к существующей рабочей базе.

```yaml
name: bank-hackathon-local

services:
  db:
    image: postgres:17-alpine
    environment:
      POSTGRES_DB: ${POSTGRES_DB:-hackathon_demo}
      POSTGRES_USER: ${POSTGRES_USER:-hackathon_app}
      POSTGRES_PASSWORD: ${POSTGRES_PASSWORD:?Set POSTGRES_PASSWORD in local .env}
    ports:
      - "127.0.0.1:5433:5432"
    volumes:
      - hackathon_pgdata:/var/lib/postgresql/data
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U $${POSTGRES_USER} -d $${POSTGRES_DB}"]
      interval: 5s
      timeout: 3s
      retries: 20
    restart: unless-stopped
    networks:
      - hackathon

  api:
    build:
      context: ./backend
    env_file:
      - .env
    environment:
      DATABASE_URL: ${DATABASE_URL}
      APP_ENV: ${APP_ENV:-local}
      FRONTEND_ORIGIN: ${FRONTEND_ORIGIN:-http://localhost:5173}
    ports:
      - "127.0.0.1:8000:8000"
    depends_on:
      db:
        condition: service_healthy
    restart: unless-stopped
    networks:
      - hackathon

  web:
    build:
      context: ./frontend
    ports:
      - "127.0.0.1:5173:80"
    depends_on:
      - api
    restart: unless-stopped
    networks:
      - hackathon

volumes:
  hackathon_pgdata:

networks:
  hackathon:
    name: bank-hackathon-local
    driver: bridge
```

В Compose для более строгой локальной изоляции можно убрать `ports` у БД, если участникам не нужен прямой доступ из IDE; приложение всё равно подключается к `db:5432` внутри Compose-сети. В тестовом/production-окружении не использовать этот пример без адаптации секретов, TLS, сети, backup и доступа.

Команда `docker compose down -v` удаляет данные именованного тома Compose. Выполнять её только если осознанно нужно сбросить локальные данные этого хакатон-проекта. Не использовать её для чужих Compose-проектов.

## 9. Пример Dockerfile для API

Версию образа Python синхронизировать с реально выбранной версией и lock-файлом. Не копировать `.env` внутрь образа.

```dockerfile
FROM python:3.14-slim

ENV PYTHONDONTWRITEBYTECODE=1 \
    PYTHONUNBUFFERED=1

WORKDIR /app

RUN groupadd --system app && useradd --system --gid app app

COPY pyproject.toml uv.lock ./
RUN pip install --no-cache-dir uv && uv sync --frozen --no-dev --no-install-project

COPY app ./app
COPY migrations ./migrations
COPY alembic.ini ./

USER app
EXPOSE 8000
CMD ["uv", "run", "uvicorn", "app.main:app", "--host", "0.0.0.0", "--port", "8000"]
```

До использования подтвердить, что образ `python:3.14-slim` доступен и все зависимости имеют совместимые wheels/build tooling. Для production дополнительно закреплять образ по digest, сканировать и пересобирать его по процессу обновлений.

## 10. API и OpenAPI: шаблон правил

- Версионировать публичные маршруты, например `/api/v1`.
- Называть JSON-поля и технические идентификаторы в `snake_case` или выбрать единый стиль и закрепить его в OpenAPI.
- Все идентификаторы, время, decimal-значения и nullable-поля описывать явно.
- В OpenAPI включить схемы успешных ответов, валидацию, статусы ошибок, bearer security scheme, примеры и правила пагинации.
- Генерировать frontend-типы/клиент из опубликованной спецификации; сгенерированные файлы не исправлять вручную.
- Swagger UI доступен в каждом окружении по требованиям, но само наличие Swagger не означает публичный доступ: доступ контролировать авторизацией/сетевыми правилами.
- Сервер заново проверяет права, состояние бизнес-процесса и все входящие значения независимо от frontend.
- Для событий покупки, активации и других повторяемых команд предусмотреть идемпотентность. Повтор запроса возвращает сохранённый результат, а не создаёт новую операцию.

### Общий формат ошибки

Использовать Problem Details или эквивалентный единый формат:

```json
{
  "type": "https://example.invalid/problems/business-conflict",
  "title": "Offer cannot be added to the showcase",
  "status": 409,
  "detail": "The offer conflicts with an existing offer in this period.",
  "instance": "/api/v1/showcase-periods/demo/offers",
  "code": "SHOWCASE_MCC_DATE_CONFLICT",
  "field_errors": []
}
```

`example.invalid` — зарезервированный домен-пример; заменить в проекте только на принадлежащий команде домен либо использовать локальный идентификатор URI.

Рекомендуемая семантика: `400` — синтаксически неверный запрос; `401` — нет действительной аутентификации; `403` — недостаточно прав; `404` — сущность не найдена; `409` — конфликт состояния/бизнес-правила; `422` — ошибки проверки полей. Зафиксировать выбранные правила в OpenAPI и тестах.

## 11. Шаблон тестовых данных для кейса

Использовать фиксированные, явно именованные сценарии плюс расширяющий Faker-набор с постоянным seed.

```text
demo_users:
  requester: synthetic-requester@example.invalid
  product_manager: synthetic-product@example.invalid
  analyst: synthetic-analyst@example.invalid
  operations_manager: synthetic-operations@example.invalid
  customer: synthetic-customer@example.invalid

demo_scenarios:
  - invalid_offer_missing_required_fields
  - successful_offer_approval_and_publication
  - returned_offer_new_version_and_reapproval
  - cross_role_change_requires_full_review
  - conflicting_date_and_mcc_blocks_publication
  - duplicate_offer_warning
  - customer_activation_and_selection_change
  - purchase_eligible_for_enhanced_cashback
  - purchase_gets_base_one_percent
  - repeated_purchase_event_is_idempotent
  - partial_payout_due_to_budget_limit
  - concurrent_reservations_do_not_exceed_budget
```

Значения email на `.invalid` являются демонстрационными и не предназначены для доставки. Пароли не помещать в seed-файлы и документацию: задавать локально через secret/config и показывать только тестовому оператору. В MVP+ добавить заранее подготовленные резервы состояний `reserved`, `confirmed`, `released`, `reconciliation_required`.

Faker использовать, например, с фиксированным seed в отдельной команде заполнения. Основные acceptance-тесты не должны зависеть от случайных имён, дат или сумм. Seed запускать только при явном флаге локальной/тестовой среды; production startup не должен автоматически наполнять демонстрационные данные.

## 13. Шаблон CI-пайплайна

Платформу CI выбрать по Git-хостингу команды. Пайплайн должен выполнять одинаковые проверки на pull request и перед интеграцией в основную ветку:

```text
1. Checkout source
2. Setup supported Python and Node versions
3. Install locked backend/frontend dependencies
4. Backend: Ruff format/lint + mypy
5. Frontend: ESLint + Prettier check + TypeScript check
6. Unit tests + coverage report
7. Start isolated PostgreSQL service/container
8. Apply migrations
9. Integration/API tests against PostgreSQL
10. Build frontend and backend Docker images
11. Optional: Playwright E2E against a temporary Compose environment
12. Publish test and coverage reports as CI artifacts
13. Deploy to an approved demo/test environment after checks pass
```

CI не должен использовать production-секреты для unit и обычных integration-тестов. Развёртывание выполняется только с отдельными правами и явными правилами защиты окружения. Не печатать секреты в логи. Стартовый coverage threshold можно установить на уровне 80% для строк backend, при этом критичные бизнес-сценарии перечислить отдельно: общий процент не заменяет сценарное покрытие.

### Пример GitHub Actions workflow

Ниже — каркас. Проверить актуальность `actions/*` и версий runtime при подключении репозитория; зафиксировать action по commit SHA, если этого требует политика организации.

```yaml
name: ci

on:
  pull_request:
  push:
    branches: [main]

permissions:
  contents: read

jobs:
  backend:
    runs-on: ubuntu-latest
    services:
      postgres:
        image: postgres:17-alpine
        env:
          POSTGRES_DB: hackathon_test
          POSTGRES_USER: test_user
          POSTGRES_PASSWORD: test_password
        ports:
          - 5432:5432
        options: >-
          --health-cmd "pg_isready -U test_user -d hackathon_test"
          --health-interval 5s
          --health-timeout 3s
          --health-retries 20
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-python@v5
        with:
          python-version: "3.14"
      - name: Install uv
        run: pip install uv
      - name: Install backend dependencies
        working-directory: backend
        run: uv sync --frozen
      - name: Lint
        working-directory: backend
        run: uv run ruff check .
      - name: Format check
        working-directory: backend
        run: uv run ruff format --check .
      - name: Tests and coverage
        working-directory: backend
        env:
          DATABASE_URL: postgresql+asyncpg://test_user:test_password@localhost:5432/hackathon_test
          JWT_SECRET: ci-only-secret-not-for-production-000000000000
        run: uv run pytest --cov=app --cov-branch --cov-report=term-missing --cov-report=xml

  frontend:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: "26"
          cache: npm
          cache-dependency-path: frontend/package-lock.json
      - name: Install dependencies
        working-directory: frontend
        run: npm ci
      - name: Lint
        working-directory: frontend
        run: npm run lint
      - name: Type check
        working-directory: frontend
        run: npm run typecheck
      - name: Unit tests
        working-directory: frontend
        run: npm test
      - name: Build
        working-directory: frontend
        run: npm run build
```

Python runtime `3.14` здесь допустим только после подтверждения совместимости всех зависимостей; если CI не проходит из-за поддержки пакета, изменить runtime и Dockerfile согласованно. Для GitLab CI перенести те же стадии и артефакты в `.gitlab-ci.yml`, не дублировать две конкурирующие конфигурации.

## 17. Безопасный режим хакатона: короткий чек-лист

- Только синтетические или однозначно обезличенные данные, разрешённые правилами площадки; по умолчанию никаких реальных банковских/клиентских данных.
- Не выгружать данные организации в публичные внешние AI-сервисы, paste-сайты и сторонние API без письменного разрешения.
- Не коммитить `.env`, токены, private keys, сертификаты, реальные выгрузки и дампы БД.
- Проверять авторизацию и права на backend для каждой операции; не считать frontend-доступ контролем безопасности.
- Разделять local/test/demo/production конфигурации; не использовать production-креденшелы в хакатоне.
- Применять принцип минимальных прав, параметризованные запросы, входную валидацию и безопасную обработку ошибок.
- Не записывать пароли, bearer-токены, PAN/CVV, клиентские идентификаторы и чувствительные payload в логи. PAN/CVV не должны появляться в этом прототипе вовсе.
- Ограничивать CORS разрешёнными origin, а сетевые порты локально привязывать к `127.0.0.1`, если внешний доступ не нужен.
- Удалять/сбрасывать только собственные тестовые ресурсы и собственный Compose volume; проверить цель перед destructive-командами.
- Перед показом заказчику проверить, что демонстрационная среда не подключена к production-системам и данные явно обозначены как синтетические.

## 18. Быстрый старт команды

1. Согласовать `README.md`: цель, критерий победы/приёмки, демо-путь и исключения.
2. Проверить локальные версии Python/Node/Docker и выбрать общие runtime, подтверждённые CI.
3. Создать каркас каталогов, `pyproject.toml`, lock-файлы, Compose и `.env.example`.
4. Поднять отдельную локальную PostgreSQL и проверить healthcheck/изоляцию.
5. Создать одну вертикаль: схема → миграция → backend API → OpenAPI → frontend → интеграционный тест.
6. Добавить синтетический happy path и негативные сценарии до визуальной полировки.
7. Подключить CI и coverage-отчёт до добавления большого объёма функций.
8. Подготовить инструкции и проверить их на чистом клоне/новом окружении участника.
9. Провести демонстрацию только на синтетических данных и проверить, что не используются чужие БД, секреты или внешние банковские ресурсы.

## 19. Ограничения шаблона

Шаблон ускоряет старт и уменьшает число случайных технических решений, но не заменяет системный анализ требований, threat modeling, secure code review, нагрузочные/отказоустойчивые испытания, проверку лицензий, банковскую ИБ-экспертизу и согласование интеграций. Перед переносом любого хакатонного прототипа за пределы изолированной демонстрационной среды его необходимо пересмотреть с владельцами продукта, архитектуры, ИБ, данных и эксплуатации.
