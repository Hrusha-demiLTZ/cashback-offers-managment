## 0. Как пользоваться списком

- MVP+ реализуется как конечный целевой объём кейса; пометка «MVP+» выделяет функции сверх базового сквозного MVP.
- Не подключать рабочую/чужую PostgreSQL, банковские API, настоящие клиентские данные или секреты.
- Для каждого этапа сохранить результат в Git и проверить `git status` перед коммитом.

- [ ] Идемпотентность: повтор покупки не создаёт повторный результат или списание бюджета.
- [ ] MVP+: атомарно резервировать остаток бюджета; поддержать подтверждение, отмену/освобождение, изменение суммы и состояние «требует сверки».
- [ ] Отчёты MVP+: подготовить показатели срока согласования, возвратов/циклов, состава витрины и использования бюджета.

- [ ] Добавить скрипт генерации в `package.json` и проверку CI на актуальность сгенерированных файлов.
- [ ] Настроить централизованный обработчик 401/403/409/422 и безопасное обновление UI после бизнес-конфликта.
- [ ] Не редактировать генерируемые типы вручную и не поддерживать параллельные вручную написанные копии API-моделей.

**Готово, когда:** интерфейс работает с backend по OpenAPI-контракту, а не с локальными фиктивными ответами; права и расчёты подтверждаются сервером.

## Этап 8. Подготовить синтетические данные и сценарии демонстрации

- [ ] Создать seed-команду с явным флагом окружения; не запускать наполнение автоматически в production.
- [ ] Сгенерировать только тестовых пользователей и клиентов; не импортировать реальные выписки, PAN, CVV, клиентские контакты или идентификаторы.
- [ ] Создать набор фиксированных офферов для всех состояний процесса: черновик, согласование, частичное согласование, возврат, отклонение, готовность.
- [ ] Подготовить семь готовых офферов для полной демонстрационной витрины.
- [ ] Подготовить конфликтную пару: срок действия пересекается и есть общий MCC; отдельно — контрольную пару, которая не конфликтует.
- [ ] Подготовить идентичные/схожие офферы для проверки принятого правила дубликата.
- [ ] Подготовить тестовые покупки: подходит повышенному офферу; нет активации; MCC не подходит; срок не подходит; применяется базовый 1%; превышен/исчерпан бюджет; частичное начисление.
- [ ] Для MVP+ создать сценарии конкурентных резервов: подтверждение, отмена с освобождением, повтор события, изменение суммы, резерв на сверку.
- [ ] Использовать фиксированные идентификаторы, суммы, MCC, даты и Faker seed, чтобы приёмка была повторяемой.
- [ ] Проверить повторный запуск seed: либо идемпотентное обновление демонстрационного набора, либо явно документированный сброс только данных локального проекта.
- [ ] Описать сценарии и учётные записи без паролей в `docs/demo-scenarios.md`.

## Этап 9. Написать unit-, интеграционные и E2E-тесты

### Unit-тесты доменных правил

- [ ] Валидация обязательных полей, процента, бюджета, MCC и временных границ.
- [ ] Переходы статусов и блокировка публикации при возврате/отклонении.
- [ ] Diff полей и определение обязательных зон повторной проверки.
- [ ] Расчёт процентов, правила округления, базовые 1%, ограничение бюджетом и частичное начисление.
- [ ] Проверка конфликта публикации по пересечению срока + общему MCC; проверить отдельно отсутствие каждого условия.
- [ ] Выбор основной причины неприменения повышенного оффера по установленному приоритету.

### Интеграционные тесты с PostgreSQL

- [ ] Миграции применяются к чистой БД.
- [ ] Оффер, версия, решения и audit events сохраняются со связями.
- [ ] Права проверяются на сервере для каждой роли и запрещённых операций.
- [ ] Дубликат activation/purchase не приводит к повторной записи/начислению.
- [ ] Ограничения БД не позволяют нарушить уникальность/ссылочную целостность.
- [ ] Параллельные MVP+ покупки не превышают доступный общий бюджет.
- [ ] Подтверждение и отмена резерва сохраняют ожидаемую сумму и историю.

### E2E-сценарии браузера

- [ ] Неудачное создание: валидация показывает все ошибки и сохраняет введённые значения.
- [ ] Полностью успешный путь оффера от создания до показа клиенту и подходящей покупки.
- [ ] Возврат, исправление в новой версии, diff и повторное согласование.
- [ ] Конфликт публикации и объяснение блокирующего оффера.
- [ ] Клиентская активация, повтор активации и смена выбора.
- [ ] Показ базового 1% и объяснение отказа от повышенного предложения.
- [ ] Повтор покупки и ограничение начисления остатком бюджета.
- [ ] Прямой API-запрос пользователем без подходящей роли возвращает отказ.

- [ ] Настроить pytest-cov с branch coverage и отчётами `term-missing`, XML и HTML (HTML можно публиковать CI artifact).
- [ ] Установить начальный threshold backend (например, 80%) и перечислить критичные сценарии отдельно от общего процента.
- [ ] Сформировать таблицу `требование → тесты → результат` в отчёте или `docs/test-coverage.md`.

**Готово, когда:** основные критерии ТЗ выполняются автоматическими тестами; CI показывает тестовый отчёт и понятную связь покрытия со сценариями.

## Рекомендуемый порядок параллельной работы команды

Параллелить только после согласования интерфейсов:

1. **Аналитик/владелец процесса:** закрывает матрицу полей и зон, денежные правила, статусы, причины отказа, критерии приёмки.
2. **Backend-разработчик:** готовит модель БД, миграции и API-контракт; согласует OpenAPI до массовой реализации UI.
3. **Frontend-разработчик:** готовит wireframe/экраны по утверждённому контракту, подключает сгенерированный клиент.
4. **QA/автоматизация:** оформляет сценарии приёмки, тестовые данные и проверку CI параллельно с API.
5. **DevOps/ответственный за среду:** изолирует Compose, настраивает CI, секреты и тестовое развёртывание.

Даже если один участник выполняет несколько ролей, решения о контракте, схеме и критериях ошибок нужно согласовать до того, как frontend и backend реализуют несовместимые предположения.

## Зависимости между этапами

```text
Окружение и Git
  -> бизнес-решения и критерии
  -> backend-каркас + модель БД + OpenAPI
  -> отдельная PostgreSQL + миграции
  -> API, роли и бизнес-правила
  -> frontend по сгенерированному API-клиенту
  -> seed + интеграционные/E2E-тесты
  -> CI/CD + инструкции
  -> финальная демонстрация
```

Compose, lint, тестовый каркас и CI следует поднимать уже в начале, но полноценная бизнес-реализация не должна опережать решения по версиям, деньгам, авторизации и OpenAPI.
