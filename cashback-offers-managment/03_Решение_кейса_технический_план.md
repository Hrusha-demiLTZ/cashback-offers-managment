# Решение кейса: технический план реализации

> **Статус:** рекомендуемый план прототипа по материалам диалога и исходным документам. Это не описание уже реализованной системы и не утверждение промышленной архитектуры. Код приложения в рамках текущей задачи не создаётся.

## 1. Назначение и цель

Цель — подготовить прототип для демонстрации заказчику полного пути управления оффером повышенного кэшбэка: создание, проверка и согласование, исправление с сохранением версий, публикация в тестовой витрине, выбор клиентом и расчёт тестовой покупки.

Решение должно запускаться локально, предоставлять русскоязычный адаптивный интерфейс, использовать синтетические данные и включать автоматизированные проверки и понятные инструкции. Архитектура должна оставлять возможность дальнейшего развития, но не вводить сложность, не нужную прототипу.

В репозитории на момент подготовки плана находятся исходное задание, подробное ТЗ и рабочие рассуждения. Исходного приложения и выбранного ранее стека нет. Версия Python, обнаруженная в окружении компьютера: **3.14.7**. Её совместимость с выбранными библиотеками необходимо подтвердить в CI до фиксации версии проекта.

## 2. Границы MVP и MVP+

### В MVP включить

- создание и редактирование черновика оффера;
- проверку обязательных полей и понятные сообщения об ошибках;
- отправку неизменяемой версии оффера на параллельное согласование;
- решения продуктового менеджера, аналитика и операционного менеджера с обязательными комментариями;
- возврат на доработку, отклонение, повторную отправку, историю версий и действий;
- отображение причин блокировки и состояния согласования по ролям;
- отдельный переход из состояния «согласован» в «готов к запуску»;
- ручное включение готовых офферов в демонстрационный период витрины;
- до семи повышенных офферов и отдельную обязательную категорию «1% на всё»;
- проверку конфликтов офферов по пересечению сроков действия и наличию общего MCC;
- синтетических клиентов, активацию и смену выбора оффера;
- тестовые покупки, объяснимый результат расчёта, базовый 1% для покупок, не покрытых повышенным оффером;
- защиту от повторной обработки одной покупки и повторной активации.

### В MVP+ включить

- настраиваемый ручной/полуавтоматический отбор и объяснимые приоритеты для витрины, без ML;
- простые синтетические сегменты/подписки только с зафиксированными демонстрационными правилами;
- отчёты по срокам и исходам согласования, замечаниям, составу витрины и использованию бюджета;
- резервирование общего бюджета при конкурентной обработке тестовых покупок, подтверждение резерва, его освобождение при отмене до подтверждения и идемпотентность событий;
- очередь/представление для резервов, требующих сверки.

### Не входит

Реальные банковские, процессинговые, карточные и бухгалтерские интеграции; реальные денежные операции; настоящее мобильное банковское приложение; ML-персонализация; кабинет внешнего партнёра; промышленная обработка возвратов и оспариваний. Все клиенты, покупки и начисления в прототипе синтетические и демонстрационные.

## 3. Рекомендуемый стек и форма приложения

Предлагается **модульный монолит**: единое backend-приложение с функциональными модулями, отдельный frontend и одна основная реляционная БД. Микросервисы для объёма прототипа не рекомендуются.

| Область | Рекомендуемое решение |
|---|---|
| Backend | Python 3.14.7 как исходный кандидат; FastAPI, Pydantic, SQLAlchemy 2, Alembic |
| Frontend | React, TypeScript, Vite |
| Компоненты интерфейса | MUI либо сопоставимая библиотека; русскоязычный адаптивный интерфейс |
| База данных | PostgreSQL, отдельный экземпляр для кейса |
| Redis | Не включать в базовую конфигурацию; добавить только при подтверждённой потребности |
| Контракт API | OpenAPI/Swagger; TypeScript-клиент генерировать из спецификации |
| Синтетические данные | Фиксированные демонстрационные сценарии и Faker для дополнительных данных |
| Локальное окружение | Docker Compose |
| Автоматизация | CI-пайплайн с lint, тестами, отчётом о покрытии и сборкой |

Python 3.14.7 установлен в текущем окружении, однако совместимость версий FastAPI, SQLAlchemy, драйвера PostgreSQL и средств тестирования необходимо проверить в CI. Если необходимая зависимость не поддерживает выбранную версию, следует зафиксировать ближайшую совместимую поддерживаемую версию Python единообразно в проекте, контейнерах и пайплайне.

Выбор платформы CI не фиксируется: у текущего репозитория нет настроенного remote, поэтому GitHub Actions или GitLab CI нельзя считать уже выбранными. Платформу следует определить при подключении репозитория к хостингу.

## 4. Данные и PostgreSQL

PostgreSQL — единственный источник истины для пользователей, ролей, состояний оффера, решений, активаций, покупок, результатов и бюджета. Redis не требуется для этого прототипа. Конкурентный учёт бюджета лучше обеспечивать транзакциями и ограничениями PostgreSQL; Redis не должен быть единственным хранилищем критичного бизнес-состояния.

Для независимости от уже имеющегося на компьютере PostgreSQL использовать отдельный контейнер в Docker Compose:

- отдельный контейнер и зафиксированный образ PostgreSQL;
- отдельную базу данных и пользователя приложения;
- отдельный именованный Docker volume;
- отдельный локальный порт, например `5433`, если порт свободен;
- отдельные секреты для окружения кейса;
- отсутствие подключения к существующей базе проекта или доступа к её учётным данным.

Миграции схемы должны быть версионируемыми и выполняться управляемой командой/шагом деплоя. Миграции — источник истины для структуры БД; ручные SQL-файлы не должны становиться параллельным неуправляемым способом изменения схемы.

### Основные сущности данных

- `User` и `Role` — синтетические пользователи и назначенные сервером роли.
- `Offer` — заявка и её текущий статус.
- `OfferVersion` — неизменяемый снимок отправленных на проверку полей.
- `ApprovalDecision` — решение, комментарий, роль, проверяемая версия и зона.
- `ShowcasePeriod` и `PeriodOffer` — период витрины и включённые офферы.
- `Client` — синтетический клиент.
- `Activation` — выбор оффера клиентом, категорией и периодом; история смены выбора сохраняется.
- `TestPurchase` и `CashbackResult` — демонстрационная покупка и результат проверки/расчёта.
- `BudgetEntry` и `BudgetReservation` — учтённые начисления и резервы бюджета MVP+.
- `AuditEvent` — добавочная история важных действий и переходов.

Для денег использовать точный десятичный тип, не `float`. Для MCC — строковый код фиксированного формата. Временные значения передавать в ISO 8601 с временной зоной и хранить единообразно; интерфейс отображает их в московском времени.

Ограничения целостности должны защищать, как минимум, ссылочную целостность, повторную обработку идентичной покупки, уникальность актуального выбора в категории/периоде и невозможность превышения бюджета при конкурентном резервировании. Проверка конфликта публикации учитывает пересечение срока действия офферов и хотя бы один общий MCC.

### История и аудит

Решения, комментарии, изменения версий, публикации, активации и расчёты проектируются как история с добавлением новых событий. Обычные операции приложения не редактируют и не удаляют исторические записи. Это не означает абсолютной неизменяемости от администратора инфраструктуры или БД: техническая защита аудита для промышленного применения требует отдельного решения по доступам, резервированию и хранению журналов.

## 5. Версии и процесс согласования

Отправка оффера создаёт неизменяемую версию. Согласующие рассматривают один и тот же снимок независимо. После возврата заказчик может подготовить отдельный черновик следующей версии; это не изменяет версию, которую ещё рассматривают другие роли. При отправке новой версии решения и комментарии предыдущей сохраняются в истории.

Не следует полагаться только на автоматический diff для принятия бизнес-решения о том, какие роли должны повторно согласовать оффер. Рекомендуется следующий механизм:

1. Backend сравнивает поля новой и предыдущей версий и формирует diff.
2. У полей имеется утверждённая таблица владельцев зон: продукт, аналитика, операции; поле может относиться к нескольким зонам.
3. По этой таблице система определяет минимально обязательные зоны повторной проверки и показывает основание маршрутизации.
4. Ответственная роль оценивает влияние исправления на остальные зоны и фиксирует решение.
5. Если влияние затрагивает другие зоны или не может быть однозначно определено, система запускает полное согласование.
6. Сохранённые одобрения незатронутых зон принимаются только по явно утверждённому правилу и с записью причины в историю.

Таким образом, diff автоматизирует обнаружение изменённых полей и помогает назначить проверки, но не заменяет профессиональное суждение согласующих. Полевая матрица и правила влияния должны быть согласованы владельцами процесса до финализации контракта.

### Роли демонстрации

Создать отдельные синтетические учётные записи автора, продуктового менеджера, аналитика, операционного менеджера и клиента. Роли проверяются на backend, а не только скрытием кнопок во frontend. Для демонстрации разделения обязанностей рекомендуется запретить автору согласовывать собственный оффер. Назначение нескольких ролей одному пользователю не включать без явной необходимости.

### Статусы

Сохраняется бизнес-модель ТЗ: черновик, на согласовании, частично согласован, нужны исправления, отклонён, согласован, готов к запуску. Статус оффера отделён от решения конкретной роли. Для запуска требуются актуальные одобрения необходимых зон, отсутствие неразрешённых замечаний, допустимый срок и проверка конфликта размещения.

## 6. Денежные правила

Пользовательская настройка задаёт рубль и московское время, а также требование рассчитывать значения с точностью до сотой копейки и показывать результат в рублях. Рекомендуемая техническая интерпретация:

- денежные значения хранятся в точном decimal-типе, не в двоичном `float`;
- внутренняя точность расчёта и точность отображения разделены;
- правило финального округления до минимальной единицы выплаты явно фиксируется до реализации;
- бюджет уменьшается на фактически учтённое начисление, а не на округлённое до целого рубля представление в интерфейсе;
- начисление ограничивается доступным остатком; последнее начисление может быть меньше расчётного;
- клиент видит фактически начисленную сумму; пояснение о частичном начислении, например «достигнут лимит оффера», показывается отдельно.

Округлять все начисления до целого рубля как единственную расчётную величину не рекомендуется: небольшие покупки могут дать неверное или нулевое отображение. Конкретное правило округления, минимальную сумму начисления и поведение остатка меньше минимальной единицы выплаты нужно зафиксировать с владельцем продукта. Не вводить бизнес-минимумы без такого подтверждения.

## 7. Синтетические данные

Для повторяемого показа фиксированные данные важнее случайной генерации. Набор состоит из:

1. Предсказуемых seed-данных для приемки и демонстрации.
2. Дополнительных синтетических записей, генерируемых Faker с фиксированным seed при необходимости.

Seed-данные включают:

- пользователей с различными ролями и маленькую группу синтетических клиентов;
- семь готовых офферов и период витрины;
- офферы в черновике, на согласовании, частично согласованные, возвращённые и отклонённые;
- конфликтующие офферы с пересечением срока и общим MCC;
- дублирующие/схожие предложения для демонстрации проверки;
- покупки для успешного начисления, базового 1%, неподходящего MCC, отсутствия активации, срока вне действия, повторной обработки и ограниченного бюджета;
- резервы MVP+, включая подтверждённый, освобождённый и требующий сверки.

В seed не использовать реальные персональные или банковские данные. Данные помечаются как демонстрационные. Повторный запуск seed не должен бесконтрольно создавать дубликаты; seed не включается для production-окружения.

## 8. API, OpenAPI и frontend

Контракт API и технические имена — на английском языке; пользовательский интерфейс и сообщения — на русском. OpenAPI должен содержать модели запросов и ответов, ограничения полей, примеры успешных и ошибочных ответов, статусы, правила авторизации и описание ключевых бизнес-ошибок. На основе спецификации генерируется TypeScript-клиент для frontend.

Предлагаемые группы API:

- authentication / current user;
- offers, drafts, validation and versions;
- approvals, decisions and comments;
- history, diff and blocking reasons;
- showcase periods, publication and conflict validation;
- client showcase and activations;
- test purchases, calculation results and idempotency;
- MVP+ reports and budget reservations.

Ошибки возвращаются в едином формате (например, Problem Details): ошибки полей, отсутствие аутентификации, недостаточные права, отсутствие сущности и конфликты бизнес-состояния должны быть различимы. Повторная отправка покупки должна иметь стабильный идентификатор/idempotency key и не создавать повторный расчёт или расход бюджета.

Swagger UI доступен в каждом окружении согласно требованию, но доступ к нему контролируется по окружению: на локальном/тестовом стенде доступен участникам, в недоверенной среде ограничивается авторизацией или сетью. Публичность документации не должна давать доступ к операциям API.

В прототипе включить аутентификацию и серверную проверку ролей. Для локальной демонстрации допустимы синтетические пользователи; способ их входа должен быть удобным для демонстрации, но не обходить проверку прав на backend. Для реальной организации способ интеграции с корпоративной идентификацией остаётся отдельным решением.

Frontend — адаптивное SPA с внутренним интерфейсом согласования и демонстрационной клиентской витриной. Внутренние комментарии и служебные данные бюджета клиенту не показываются. Смена оффера не пересчитывает прошлые покупки.

## 9. Docker и базовая безопасность

Локальный запуск должен быть коротким и описанным в одном наборе инструкций. Docker Compose поднимает frontend, backend и независимую базу PostgreSQL; миграции и тестовый seed выполняются отдельными управляемыми шагами/командами.

Базовые меры:

- база не публикуется в сеть без необходимости;
- отдельные учётные данные и секреты для каждого окружения;
- секреты не записываются в Git, образы и логи;
- приложения работают с минимально необходимыми правами;
- frontend не является границей безопасности: авторизация и валидация выполняются на backend;
- настроены health checks, управление миграциями и безопасная конфигурация CORS;
- запросы и ошибки не раскрывают пароли, токены и чувствительные данные.

Для production в дальнейшем потребуются TLS, надёжное хранилище секретов, резервное копирование и проверка восстановления, мониторинг, контроль доступа и согласованные требования ИБ. Текущий план не объявляет прототип готовым к банковской промышленной эксплуатации.

## 10. Автоматизация, тесты и покрытие

CI-пайплайн должен автоматически выполнять:

1. форматирование, lint и статическую проверку Python;
2. lint, проверку типов и сборку frontend;
3. unit-тесты правил домена;
4. интеграционные тесты с PostgreSQL;
5. сквозные тесты критичных пользовательских сценариев в браузере;
6. публикацию отчёта о покрытии и проверку установленного порога;
7. сборку Docker-образов и базовые проверки зависимостей/образов;
8. развёртывание в согласованное тестовое окружение после успешных проверок.

Можно задать стартовый порог покрытия backend, например 80% строк, с отдельным усиленным контролем ключевых доменных правил. Процент покрытия сам по себе не доказывает качество тестов: отчёт должен связывать тестовые сценарии с требованиями приёмки и показывать, какие правила проверены. Для запуска тестов не должны требоваться реальные данные или внешние банковские системы.

Понятие полной автоматизации относится к сборке, проверкам, тестам, контейнеризации и развёртыванию в разрешённую тестовую среду. Оно не означает автоматическое принятие бизнес-решений, автоматический допуск в production или отсутствие обязательного контроля изменений.

## 11. Сквозные сценарии приёмки

Интеграционными/сквозными тестами покрыть как минимум:

1. **Неудачное создание:** пропущены поля или невалидны даты, процент, бюджет либо MCC; отправка блокируется, значения не теряются, ошибки показываются у полей.
2. **Полностью успешный путь:** создание, независимые решения трёх ролей, готовность к запуску, публикация, отображение в витрине, активация, подходящая покупка и повышенное начисление.
3. **Возврат и исправление:** возврат с комментарием, новая версия, diff, повторное согласование, сохранение прежних версий и истории.
4. **Маршрутизация изменений:** изменённое поле определяет ответственную зону; влияние/неопределённость запускает полный круг согласования.
5. **Конфликт публикации:** пересекающиеся сроки и общий MCC блокируют включение конфликтующего оффера с объяснимой причиной.
6. **Одинаковые предложения:** система показывает предупреждение/результат проверки дубликата. Точное правило для полностью одинаковых полей следует определить: совпадение всех полей не всегда равнозначно конфликту по ТЗ, поэтому автоматический запрет дубликатов должен быть отдельным согласованным правилом.
7. **Смена выбора клиента:** повтор активации идемпотентен; смена выбора сохраняет историю и не пересчитывает прошлые покупки.
8. **Неподходящая покупка:** отображается одна основная причина неприменения повышенного оффера; базовый 1% применяется только согласно правилу ТЗ.
9. **Повтор покупки:** повтор одного события не создаёт повторного начисления и не расходует бюджет повторно.
10. **Ограниченный бюджет:** частичное начисление ограничивается остатком; отображается точная сумма и причина ограничения.
11. **Конкурентные покупки MVP+:** несколько параллельных запросов не превышают общий бюджет; подтверждение переводит резерв в учёт, отмена до подтверждения освобождает резерв, повтор события идемпотентен.
12. **Ролевой доступ:** пользователь без необходимой роли не может выполнять решение/публикацию даже при прямом запросе к API.

## 14. Критерий готовности прототипа

Прототип можно считать готовым к показу, когда он запускается по инструкции в Docker без подключения к существующей базе; демонстрирует согласование и версии на отдельных ролях; не допускает обхода ролевых правил через API; показывает успешные и неуспешные сценарии клиентской витрины; корректно объясняет расчёт и ограничения бюджета; имеет детерминированные синтетические данные, OpenAPI, интеграционные и сквозные тесты, отчёт о покрытии и автоматизированную сборку/проверки в CI.

Это критерий готовности демонстрационного прототипа, а не разрешение на использование в реальных банковских процессах или проведение денежных операций.
